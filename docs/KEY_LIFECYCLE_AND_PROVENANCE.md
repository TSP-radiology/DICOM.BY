# Регламент жизненного цикла ключей, защиты журнала аудита и прослеживаемости релизов (`0.9.4`)

Документ определяет криптографическую модель эксплуатации **DICOM.BY**, разделение ключевых контуров, модель угроз журнала аудита и каноническую цепочку происхождения релиза (`Build Provenance`).

---

## 1. Разделение криптографических контуров

В архитектуре **DICOM.BY** используются строго изолированные ключи разных классов, ни один из которых не переиспользуется в смежном контуре:

| Контур | Алгоритм | Назначение | Где хранится закрытый ключ |
|---|---|---|---|
| **1. Ключ псевдонимизации и печатей клиники** | `HMAC-SHA-256` (`256 бит`) | Генерация псевдонимов `PatientID`, `2.25.* UID`, сдвигов дат, печатей `.deid.json` (`seal`), `curator_hmac` и записей аудита (`entry_hmac`) | **Только локально в клинике** в защищённом контейнере Windows DPAPI (`DCMDPAP1`, привязка к `CurrentUser` или `LocalMachine` + `NTFS ACL`); никогда не покидает периметр ЛПУ |
| **2. Ключ подписи релизов и офлайн-лицензий** | `Ed25519` (`RFC 8032`, `key_id = 1fa13a53af0a7294`) | Подпись `RELEASE_MANIFEST.json`, `windows-x64.json` и офлайн-ключей активации `DICOMBY-1....` | Изолированное хранилище разработчика вне дерева репозитория; в продукте и публичном верификаторе зашит **только открытый ключ** (`e3e4a53f...`) |
| **3. Транспортные ключи PACS / ИИ (`Gateway Pro`)** | `TLS 1.2 / 1.3 (mTLS, X.509)` | Взаимная аутентификация узлов PACS и шлюза по сертификатам УЦ клиники | Защищённый каталог ключей службы шлюза с ограниченным `NTFS ACL` |
| **4. Подпись исполняемых файлов ОС (`Authenticode`)** | `OV / EV Code Signing + RFC 3161` | Системная проверка издателя средствами Windows (`Get-AuthenticodeSignature`) | Запланировано перед коммерческим тиражированием (`authenticode_code_signing = false` в `0.9.4`); до внедрения обязательна предварительная проверка `Ed25519 + SHA-256` и централизованный допуск через `AppLocker / WDAC` |

## 2. Жизненный цикл производственного ключа клиники (`HMAC-SHA-256 / DPAPI`)

1. **Генерация (`CSPRNG`):**
   - Выполняется локально на целевом сервере/АРМ командой `dicom-anon.exe --generate-key clinic.dpapi` (или `--dpapi-machine` для системной службы Windows) через системный криптографический генератор (`OpenSSL RAND_bytes` / `BCryptGenRandom`) с немедленным затиранием буфера в ОЗУ через `OPENSSL_cleanse`.
2. **Блокировка демонстрационных и вырожденных ключей (`Fail-Closed rc=3`):**
   - Ядро содержит жёсткий чёрный список всех публичных демонстрационных ключей (включая `demo_test_only.key` из `samples/verify-*`) и вырожденных ключей (повторяющийся байт, длина `< 16` байт). Попытка запуска без явного тестового флага завершается отказом с кодом `3` без создания выходных файлов.
3. **Хранение и разграничение прав:**
   - Файл `clinic.dpapi` имеет заголовок `DCMDPAP1` и расшифровывается ядром Windows (`CryptUnprotectData`) только под учётной записью оператора (`CurrentUser`) или хоста службы (`LocalMachine`). Таблица соответствия (`--mapping-out`) программно блокируется, если указан путь внутри каталога обезличенной выдачи (`rc=2`).
4. **Плановая ротация и изоляция выборок:**
   - Для каждого независимого научного исследования или внешнего контрагента рекомендуется отдельный ключ `study_<id>.dpapi` (исключает кросс-корреляцию псевдонимов между разными получателями). Плановая ротация ключа шлюза выполняется не реже 1 раза в 12 месяцев с архивацией прежнего якоря журнала `.head.json`.
5. **Действия при компрометации и восстановление:**
   - При подозрении на компрометацию учётной записи Windows или резервной копии ключа администратор ИБ генерирует новый `clinic_new.dpapi`, останавливает приём по старому ключу, отзывает доступ скомпрометированной учётной записи и перевыпускает выгрузки для открытых внешних задач с новым пространством псевдонимов `2.25.*`.

## 3. Модель угроз журнала аудита (`gateway_audit.jsonl`)

Журнал шлюза защищается на трёх уровнях:
1. **Целостность последовательности и всех записей (против повреждения и локальной правки JSONL без ключа):**
   - Каждая строка связывается полем `prev` с предыдущей записью **и** подписывается индивидуальным `entry_hmac = HMAC-SHA256(clinic_key, "dicom-anonymizer|gateway-audit-v2|" + canonical_body)`.
2. **Защита хвоста от усечения и подмены последней записи:**
   - При каждой записи атомарно обновляется файл вершины `<audit>.head.json` (`entries`, `head_sha256`, `head_hmac`). Модификация последней строки, удаление хвоста или подстановка незакреплённого файла детерминированно отвергаются (`rc=1`) и `dicom-verify.exe --audit`, и открытым `dicom_by_verify.py --audit`.
3. **Защита от привилегированного локального администратора:**
   - Если локальный администратор одновременно имеет права чтения DPAPI-ключа службы и записи на локальный диск, любая чисто локальная симметричная схема пересчитываема. Для защиты от этой угрозы в промышленном контуре `Gateway Pro` файл вершины `.head.json` (не содержащий ПДн — только счётчик и `SHA-256`) периодически реплицируется на внешний `SIEM / Syslog-TLS / WORM`-контур ИБ-службы, откуда его `head_sha256` передаётся в `--audit-head` при независимой ревизии.

## 4. Каноническая прослеживаемость релиза (`Release Provenance`)

Единым корнем доверия каждого выпуска является подписанный `Ed25519` паспорт **`RELEASE_MANIFEST.json`** (`schema_version = 2.3`), синхронно публикуемый:
- на `https://dicom.by/updates/release-manifest.json`;
- в корне публичного репозитория `https://github.com/TSP-radiology/DICOM.BY` (ветка `main` и тег релиза `v0.9.4`);
- в активах GitHub Release `v0.9.4` вместе с `DICOM-BY-0.9.4-Setup.exe`, `windows-x64.json`, `sbom-0.9.4.cdx.json` и `SHA256SUMS.txt`.

Паспорт связывает одной криптографической подписью `Ed25519`:
- `SHA-256` и точный байтовый размер установщика `DICOM-BY-0.9.4-Setup.exe` и архива `Gateway Pro`;
- `SHA-256` всех четырёх бинарных модулей (`DICOM-BY.exe`, `dicom-anon.exe`, `dicom-verify.exe`, `dicom-anon-gateway.exe`), всех 8 файлов моделей `ONNX` и всех нормативных файлов `standard/`;
- `SHA-256` спецификации `SBOM.cdx.json` (`CycloneDX 1.5`), открытого верификатора `dicom_by_verify.py`, документа `DICOM_CONFORMANCE_STATEMENT.md`, когорты `tcia_cohort_237_manifest.json` и вершины эталонного аудита `sample_audit_head_sha256`.

Ядро C++17 поставляется в виде закрытых скомпилированных бинарных файлов, проверяемых как воспроизводимый **чёрный ящик (`Black-Box Reproducible Release`)** на нейтральном `windows-latest` раннере GitHub Actions (не как сборка из открытых исходников).
